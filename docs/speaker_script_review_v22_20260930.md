# v22 발표 대본 검토 기록 (2026-09-30)

## 판정

**v22에 맞춘 구조와 발표 흐름은 잘 구축되어 있다. 다만 실제 실습 안내와 사실 표현에 보완이 필요하므로, 현재 상태를 최종 검토 통과로 보지는 않는다.** 슬라이드별 대본을 전면 재작성할 필요는 없다. 아래 네 가지 우선 보완과 두 가지 권장 보완을 해당 위치에서 처리하면 된다.

이 기록은 검토 결과이며, 대본·슬라이드·안내문 원본은 수정하지 않았다. 후속 요청에 따라 검토 기록을 GitHub에 반영한다. 보완 항목은 아직 원본에 적용하지 않았다.

- 근거: [Gem 공식 도움말](https://support.google.com/gemini/answer/15146780), [Google 계정 국가별 나이 기준](https://support.google.com/accounts/answer/1350409).

## 우선 보완 2. 파일 저장 안내와 GitHub Pages 기본 주소 연결

- 위치: `docs/03_speaker_script.md:529`(2부 24쪽), `practice/README.md:87`, 인쇄용 안내문 뒷면의 파일 저장 순서.
- 안내문은 파일을 `cafe-order.html`로 저장하게 한다. 슬라이드는 `아이디.github.io/cafe-order`라는 저장소 기본 주소를 안내하지만, 그 주소에서 자료가 열리게 하는 진입 파일과 게시 위치를 설명하지 않는다.
- 영향: 안내대로 파일을 올린 뒤 기본 주소를 열면 연습 자료가 나오지 않을 수 있다. README가 있으면 자료 대신 README가 나오고, 진입 파일이 없으면 오류가 날 수 있다.
- 제안 발화: “내 PC에서 확인한 파일은 배포할 때 `index.html`로 저장소의 맨 위에 올립니다. Pages에서 게시할 브랜치와 폴더를 지정하고, 배포가 끝난 뒤 실제 주소를 열어 확인합니다.”
- 대안: 파일명을 유지하려면 공유 주소에 `/cafe-order.html`까지 포함한다. 처음 만드는 교사에게는 `index.html`로 통일하는 편이 단순하다.
- 함께 고칠 것: 대본, 복사용 안내, 안내문 HTML·PDF. 슬라이드는 공간이 허용되면 파일명 한 줄을 보완한다.
- 근거: [GitHub Pages 사이트 만들기](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site). 진입 파일은 `index.html`, `index.md`, `README.md` 중 하나이며 게시 소스의 최상위에 있어야 한다.

## 우선 보완 3. 새 대화 검토에 기준과 결과물을 전달하는 절차

- 위치: `docs/03_speaker_script.md:521`(2부 23쪽), 1부 30쪽과 Q9의 같은 안내.
- 새 대화에서 “DESIGN.md 기준으로 검토해 줘”라고 요청하도록 하지만, 검토할 기준 파일과 결과물을 전달하라는 설명이 없다. 특히 실습은 로컬 폴더를 자동으로 읽는 도구가 아닌 브라우저 채팅 AI로 진행한다.
- 영향: 새 대화가 해당 파일과 결과물을 보지 못하면 일반적인 조언만 하거나 검토를 진행할 수 없다. 같은 프로젝트의 새 대화라도 최신 결과물 전달 여부를 확인해야 한다.
- 제안 발화: “새 대화에는 DESIGN.md와 최신 HTML 파일을 함께 첨부하고 검토를 요청합니다. 화면 캡처는 배치 검토에, HTML 파일은 코드 검토에 씁니다. 실제 동작은 우리가 직접 눌러 확인합니다.”
- 함께 고칠 것: 대본 1부 30·2부 23, Q9, 필요하면 실습 안내에 복사용 검토 요청 추가.

## 우선 보완 4. 자유 선택과 정답이 있는 과제의 오류 피드백 구분

- 위치: `docs/03_speaker_script.md:394`(2부 8쪽), 2부 12쪽. PDF 8쪽은 음료·크기를 고르는 흐름에 “두 번 틀리면 정답 버튼”을 적용한다.
- 현재 카페 흐름에는 특정 음료나 크기를 고르라는 과제가 없다. 자유롭게 원하는 음료를 고르는 활동에는 하나의 정답 음료가 없다. 잘못 누른 조작과 학습 과제의 오답을 구분해야 한다.
- 영향: AI가 임의로 정답 음료를 정하거나, 학생의 선호 선택을 틀린 선택으로 처리하는 자료를 만들 수 있다.
- 제안 발화: “원하는 음료를 고르는 활동에서는 어느 음료도 오답이 아닙니다. 잘못 눌렀다면 이전으로 돌아가 선택을 바꿀 수 있게 합니다. ‘큰 컵을 골라 주세요’처럼 정답이 있는 과제에서만 힌트와 정답 강조를 사용합니다.”
- 함께 고칠 것: 대본, 2부 8·12쪽 HTML·PDF, 관련 흐름·개요 문구.

### 1부 17쪽: 컨텍스트 설명의 단정 완화

`docs/03_speaker_script.md:146`의 “지금 대화창에 보이는 내용만”, “새 대화에서는 아무것도 모르는 상태”는 같은 대본의 프로젝트 지침·파일 설명과 충돌한다. 곧이어 기억 기능의 예외를 설명하지만, 핵심 정의부터 “AI는 현재 전달된 지침·자료·대화 범위 안에서 작업하며, 새 대화에 이전 작업의 세부사항이 모두 전달되는 것은 아닙니다”로 바꾸면 더 일관적이다. 파일을 남기는 것뿐 아니라 AI가 실제로 읽게 해야 한다는 설명도 연결한다.

### 1부 29쪽: 핵심 발화와 선택 설명 분리

현재 본문은 약 1,300자(표기·줄바꿈 포함)로 1부에서 가장 길다. 규칙·스킬·훅의 구분 외에 세 도구의 옛 기능, Gem의 향후 전환, 스킬의 장점까지 기본 발화로 들어 있다. 첫 구분과 학교 사례 하나를 핵심 발화로 남기고, 제품별 전환 연혁은 `[선택 설명]`으로 옮기는 것이 좋다. “시간이 부족할 때” 목록에도 29쪽을 포함한다. 이는 발표 리허설로 시간을 측정한 결과가 아니라, 본문 분량과 주제 수에 따른 밀도 판단이다.

Q12의 “처음에는 규칙과 개요 두 가지면 충분”은 시작 단계로는 맞지만, 1부 33쪽·2부 29쪽의 파일 네 개와 연결이 약하다. “시작은 두 문서, 화면을 만들면서 DESIGN.md와 HANDOFF.md를 더해 최종적으로 네 파일을 남깁니다”라고 설명하면 혼선을 줄인다.

## 추가 사실 확인의 상태

- 재확인: Codex AGENTS.md의 공통·프로젝트 적재 순서, 스킬의 점진적 공개와 `.agents/skills` 경로, 커스텀 프롬프트의 deprecated 안내, Claude Code의 AGENTS.md 조건부 지원, 개인 계정 Gem의 2026년 11월 전환 안내, WCAG 2.2의 대상 크기 기준.
- Claude Code 대본의 설명 방향은 맞지만, v2.1.277 이상 및 프로젝트 지침 설정 등 조건은 출처 문서에 있으므로 시연 전 실제 환경에서 확인한다. DESIGN.md 같은 일반 문서가 파일명만으로 모든 도구에서 자동으로 읽히는 것은 아니므로 읽도록 요청하는 실습 안내를 유지한다.
- WCAG의 24·44는 CSS 픽셀 기준이며 예외 조건이 있다. 64px은 이 강의의 시작 기준으로 제안한 값이지 WCAG 의무 기준이 아니다. 대본은 권장 값으로 설명하고 있어 이 구분은 대체로 적절하다.
- 이번 조회에서 일부 외부 문서(해커톤 수상 사례, Stitch 공개 글, Antigravity 등)는 본문을 가져오지 못했다. 기존 출처를 확인했지만 해당 주장까지 새로 검증했다고 판정하지 않는다. 링크 조회 실패만으로 사실 오류로 분류하지 않았다.

## 후속 수정 범위

핵심 구조를 유지한 국소·중간 영향도 수정이 적절하다. 우선 보완을 처리하면 대본·출처·실습 안내·영향받는 슬라이드와 안내문을 함께 맞추고, 수정 페이지를 다시 출력해 확인한다. 전체 순서나 디자인 시스템을 바꿀 필요는 없다.

이번 문제는 기존 지침의 “정보 정확성”, “실제 실습 가능성”, “특수교육 현장 적합성”으로 설명할 수 있다. 검토 단계에서 새 지침을 추가하지 않았다. 후속 수정 중 동일 유형이 반복된다면 국가·계정별 이용 조건과 파일 저장→배포 절차의 연결을 기존 검증 규칙에 짧게 반영할지 판단한다.

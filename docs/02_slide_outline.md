## 1부. 문제 정의와 AI 작업환경

| 쪽 | 제목 | 목적 · 말할 핵심 |
|---:|---|---|
| 1 | 표지 | 코딩 기술이 아니라, 학교의 작은 불편을 AI와 함께 도구로 해결하는 연수임을 밝힌다 |
| 2 | 1부에서 함께 볼 다섯 가지 | 앞 두 묶음은 '무엇을 만들지', 뒤 세 묶음은 'AI에게 어떻게 맡길지'다 |
| 3 | 01 작은 불편에서 시작한다 | 구분 |
| 4 | 검색해서 따라 하던 일을 이제는 도구로 만든다 | 예약 종료 명령어 검색 → 버튼 프로그램. 말로 설명해 AI가 코드를 쓰게 하는 방식을 흔히 '바이브코딩'이라 부른다 |
| 5 | 학교에는 이런 작은 불편이 많다 | [질문] 이번 주에 '또 이걸 하네' 싶었던 일은? 실습 주제의 후보가 된다 |
| 6 | 좋은 문제는 작고, 분명하고, 확인할 수 있다 | '생활 전반 관리 앱'은 완성을 알 수 없고, '하차 벨 연습'은 끝까지 해 보는지로 확인된다 |
| 7 | 문제를 한 문장으로 적어 본다 | 네 칸을 못 채우면 아직 만들 준비가 안 된 것이다. 실습에서 가장 먼저 쓴다 |
| 8 | 무엇을 만들지는 사용 조건이 정한다 | 학교 PC 설치 제한과 개인정보가 특히 중요하다. 오른쪽 칸을 채워 AI에게 준다 |
| 9 | 조건이 바뀌면 만드는 방식이 바뀐다 | 태블릿=웹앱, 전원 제어=설치형, 공유 기록=저장소·로그인·개인정보 검토. 첫 도구는 웹 페이지로 |
| 10 | 02 AI와 말이 통하는 최소 지식 | 구분. 외우는 시간이 아니라 AI의 질문을 알아듣는 정도만 다룬다 |
| 11 | 웹앱과 설치형 프로그램 | 예약 종료가 설치형이어야 했던 이유(컴퓨터 기능 사용)를 연결한다 |
| 12 | 보이는 화면, 보이지 않는 처리, 남는 기록 | 홀·주방·창고 비유. 오늘 자료는 '홀만 있는 식당'이면 충분하다 |
| 13 | API와 MCP | MCP는 공식 소개에서도 'AI용 USB-C 포트'에 비유한다. 연결할수록 권한 관리가 필요하다 |
| 14 | GitHub와 배포 | 되돌리기가 GitHub의 가장 큰 장점이다. 무료 Pages는 공개라서 학생 정보는 넣지 않는다 |
| 15 | 개발 지식은 AI의 질문에 답할 때 쓴다 | 조건을 모르면 AI가 임의로 정하고, 그 결과가 교실에 맞지 않는다 |
| 16 | 무엇으로 만들지 모르면 조건을 주고 비교를 부탁한다 | 비교 기준을 함께 주는 것이 핵심. 최종 결정은 교사가 한다 |
| 17 | 03 질문 한 번에서 작업환경으로 | 구분 |
| 18 | 대화가 길어지면 AI는 기준을 놓친다 | AI는 지금 대화에 보이는 것(컨텍스트)만 참고한다. 새 대화는 처음부터다 |
| 19 | 좋은 질문 한 번보다 좋은 작업환경이 오래 간다 | 기준을 파일에 두면 내일 새 대화도, 다른 선생님도 같은 기준으로 이어 간다 |
| 20 | 하네스: AI가 믿을 만하게 일하도록 갖춘 환경 | OpenAI 팀의 경험: 사람의 일이 코드 작성에서 환경·의도·확인 구조 설계로 바뀌었다. 에이전트=스스로 파일을 읽고 도구를 쓰는 AI |
| 21 | 결과가 나쁠 때 '더 잘해'라고 하지 않는다 | '더 열심히'는 해결책이 아니었다. 무엇이 빠졌는지 묻고 파일로 채운다 |
| 22 | 해커톤 우승자가 공개한 것은 '작업환경'이었다 | ECC는 공식 표준이 아니라 개인 공개 사례. 설치가 아니라 구조를 본다 |
| 23 | 문제를 가장 잘 아는 사람이 도구를 만든다 | 의사·수리 기사·교육자·목수의 아들. 현장 지식이 곧 경쟁력이다 |
| 24 | 현장 지식을 파일로 정리하자 AI의 판단이 좋아졌다 | 지시문은 그대로, 파일 하나로 74%→81%. 교사의 학생 이해도 이런 파일이 된다 |
| 25 | 04 작업환경을 이루는 것들 | 구분 |
| 26 | 작업환경은 학교 업무 체계와 닮았다 | 규칙·편람·매뉴얼·담당자·장비·인수인계로 한 번에 지도를 그린다 |
| 27 | 규칙 파일: 매번 말하지 않아도 지킬 것 | 짧을수록 잘 지킨다. 같은 부탁을 두 번 하면 한 줄 더할 때다 |
| 28 | 도구 이름은 달라도 같은 파일을 쓸 수 있다 | Claude Code는 CLAUDE.md가 없으면 AGENTS.md를 읽는다. 2026. 9. 공식 문서 기준 |
| 29 | 프로젝트 문서: AI가 알아야 할 배경 | '하지 않는 것'을 적으면 AI가 일을 키우지 않는다 |
| 30 | 스킬: 자주 하는 일을 매뉴얼로 만든다 | 규칙은 항상 읽고, 스킬은 필요할 때 읽는다 |
| 31 | 에이전트: 일이 커지면 역할을 나눠 맡긴다 | 작은 자료는 AI 하나로 충분. 검토만 새 대화에 맡겨도 효과가 크다 |
| 32 | 도구 연결: AI가 직접 열어 보고 확인하게 한다 | ChatGPT '앱', Claude '커넥터'도 같은 역할. 연결할수록 권한이 커진다 |
| 33 | 완료 기준을 먼저 주면 AI가 스스로 확인하고 고친다 | 반복(루프)에는 멈출 기준이 필요하다. 세 번 실패하면 사람에게 넘긴다 |
| 34 | 처음에는 이만큼만 갖추면 된다 | 파일 네 개와 필요할 때의 스킬 폴더. 문제가 반복될 때 한 줄씩 늘린다 |
| 35 | 05 작업공간과 인계 | 구분 |
| 36 | 프로젝트마다 폴더 하나를 만든다 | 숨김 설정 폴더와 내 프로젝트 폴더를 구분하고, 도구에서 '폴더 열기'로 연다. GitHub에 올릴 폴더는 영어 이름이 편하다 |
| 37 | 공통 규칙과 이 프로젝트의 규칙을 나눈다 | Codex는 전역 파일 뒤에 저장소 루트부터 현재 폴더까지 합쳐 읽는다 |
| 38 | 대화가 길어지면 인계 파일을 쓰고 새 대화로 넘긴다 | 채팅 전체가 아니라 핵심 상태만 넘긴다 |
| 39 | 인계 파일은 이렇게 짧아도 충분하다 | '안 된 방법'이 같은 실패를 막는다(예: 태블릿 자동 재생 차단) |
| 40 | 이 강의자료도 같은 방식으로 만들었다 | 오늘 슬라이드가 만들어진 저장소가 곧 작은 하네스 예시다 |
| 41 | 처음 요청할 때 쓰는 문장 | 바로 만들지 말고 질문과 문서 초안부터 |
| 42 | 이어서 작업할 때 쓰는 문장 | 한 번에 하나, 완료 기준, 확인 결과, 인계 갱신 |
| 43 | 1부에서 가져갈 세 가지 | 2부 예고: 학생이 헤매지 않는 화면 |
| 44 | 참고 자료 | 도구 기능·요금은 사용 전에 다시 확인한다 |

## 2부. UX/UI 설계와 구현·검증 실습

| 쪽 | 제목 | 목적 · 말할 핵심 |
|---:|---|---|
| 1 | 표지 | 1부의 문제 한 문장과 작업환경 위에 실제로 쓰이는 화면을 올린다 |
| 2 | 2부에서 함께 할 여섯 가지 | 설계 → 기준 파일 → 시안 → 구현·확인·공개 → 실습 |
| 3 | 01 잘 돌아가는 것과 잘 쓰이는 것은 다르다 | 구분 |
| 4 | AI는 그럴싸한 화면을 빠르게 만든다 | 판단 기준은 하나: 우리 학생이 혼자 끝까지 할 수 있는가 |
| 5 | 예: "영화 예매 사이트처럼 만들어 줘"의 첫 결과 | 실제 서비스를 복사하면 연습 자료가 복잡해진다 |
| 6 | 교사가 다듬으면: 연습할 행동이 보이는 화면 | 줄이는 것이 아니라 단계를 설계하는 것. 익숙해지면 선택지를 늘려 실제에 가깝게 |
| 7 | UX는 사용하는 과정, UI는 보이는 화면 | 행사 동선과 표지판 비유. 흐름을 먼저 정한다 |
| 8 | 화면보다 흐름을 먼저 그린다 | 실수했을 때 어디로 가는지가 특수교육 자료에서 가장 중요하다 |
| 9 | 흐름을 글로 적어 주면 AI가 정확히 만든다 | 두 번 틀리면 정답을 강조하는 규칙은 교사만 정할 수 있다 |
| 10 | 02 우리 학생을 위한 화면 원칙 | 구분. 원칙은 출발점, 기준은 우리 학생 |
| 11 | 특수교육 자료의 화면 원칙 | 여섯 원칙을 모두 읽지 말고, 우리 반에 가장 중요한 두 가지를 고르게 한다 |
| 12 | 같은 자료도 학생에 따라 조절할 수 있게 만든다 | 교사용 설정으로 선택지 수·소리·가격 계산을 바꾼다 |
| 13 | 틀렸을 때의 화면이 학습을 결정한다 | 도움을 단계적으로 늘린다. 빨간 X와 경고음만 주는 화면은 피한다 |
| 14 | 03 DESIGN.md: 화면 기준을 파일로 | 구분 |
| 15 | DESIGN.md는 AI를 위한 화면 기준서다 | Google Stitch가 2026. 4. 형식을 공개(alpha). 위는 값, 아래는 이유 |
| 16 | DESIGN.md 예시: 학습자료 화면 | 초안은 AI가 쓰고 교사는 기준을 고친다. 이 강의자료의 DESIGN.md도 같은 형식이다 |
| 17 | DESIGN.md를 만드는 요청문 | '고칠 곳을 알려 달라'는 줄이 교사의 판단이 들어갈 자리를 만든다 |
| 18 | 04 코드보다 먼저 그림으로 확인한다 | 구분 |
| 19 | 코드로 고치기 전에 그림으로 실패해 본다 | 그림은 버리면 되지만 코드는 고칠수록 꼬인다 |
| 20 | 시안 도구는 필요한 만큼만 고른다 | 오늘은 그림 시안이면 충분하다. 도구는 필요할 때 한 단계씩 |
| 21 | 그림 시안은 이렇게 요청하고 이렇게 고친다 | 그림 속 한글은 틀릴 수 있다. 배치와 크기를 본다 |
| 22 | Google Stitch와 Claude Design: 눌러 보는 시안 | Claude Design은 유료 플랜 연구 프리뷰. 반드시 써야 하는 도구는 아니다 |

| 25 | 05 만들고, 확인하고, 공개한다 | 구분 |

| 28 | 검토와 검증은 다르다 | '완료했습니다'는 검증이 아니다. 검토는 새 대화에 맡기면 더 잘 보인다 |
| 29 | 교사가 직접 하는 5분 확인 | 일부러 틀리게 누르기와 실제 태블릿 확인이 가장 많이 문제를 찾는다 |

| 33 | 실습 주제: 3~5단계로 끝나는 장면 하나 | 1부에서 적은 문제 한 문장을 그대로 써도 된다 |

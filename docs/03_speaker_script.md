# 강릉오성학교 연수 - 슬라이드별 발표 대본

이 파일은 슬라이드 화면에 적힌 내용을 읽는 원고가 아니라, **왜 이 장을 보여주는지와 어떤 예시를 덧붙일지**를 설명하는 강사용 대본이다.

## 01. 프롬프트를 넘어, AI와 함께 만드는 교사의 도구

오늘 연수의 출발점은 코딩 자체가 아니다. 선생님들이 이미 갖고 있는 학생 이해와 수업·생활지도 경험을 AI가 실행할 수 있는 형태로 바꾸는 방법을 다룬다. 단발성 프롬프트를 잘 쓰는 요령보다, AI가 프로젝트를 이해하고 반복해서 같은 기준으로 일하도록 만드는 구조를 중심으로 설명한다. 마지막에는 오성학교 현장에서 바로 써볼 수 있는 작은 웹자료를 직접 설계하고 구현하는 흐름까지 연결한다.

**근거:** [1]

## 02. 오늘 가져갈 세 가지

도구 이름을 많이 외우는 연수가 되지 않도록 세 가지 결과를 먼저 제시한다. 첫째, AI에게 반복 지시하지 않아도 되는 환경을 만든다. 둘째, 특수교육 교사의 도메인 지식을 UX 결정으로 바꾼다. 셋째, 작은 아이디어를 실제 주소가 있는 웹자료까지 가져가는 전체 과정을 한 번 경험한다. 이후 나오는 Claude Code, Codex, Antigravity, Figma, Stitch 등은 이 세 목적을 위한 선택지로 본다.

**근거:** [1]

## 03. AI 활용의 중심이 이동하고 있다

생성형 AI 초기에 가장 많이 강조된 것은 프롬프트 작성법이었다. 하지만 프로젝트가 길어지면 ‘이번 한 번의 답’을 잘 받는 것보다, AI가 우리 프로젝트의 원칙과 자료를 계속 참고하게 만드는 것이 더 중요해진다. 같은 설명을 매번 붙여 넣지 않고, 프로젝트 안에 규칙·설계 문서·작업법·검증 기준을 남겨 두는 방식이 점점 중요해지고 있다. 이것이 뒤에서 설명할 하네스 사고방식이다.

**근거:** [1], [8]

## 04. 바이브코딩을 다시 정의해 보기

바이브코딩을 ‘코딩을 하나도 몰라도 무엇이든 만든다’로 이해하면 결과물이 그럴싸한 데서 멈추기 쉽다. 코드 작성 비중은 AI가 가져가지만, 사용자와 문제를 정의하고 기능 범위를 줄이고, 실패했을 때 무엇을 고쳐야 할지 판단하는 역할은 더 중요해진다. 즉 코딩 지식이 완전히 사라지는 것이 아니라, 사람의 역할이 구현에서 설계와 판단 쪽으로 이동한다고 보는 편이 정확하다.

**근거:** [1]

## 05. 특수교육 교사의 도메인 지식은 강력한 입력이다

여기서 오성학교 선생님들의 강점이 분명해진다. AI는 버튼을 만들고 화면을 꾸밀 수 있지만, 특정 학생이 세 개의 선택지에서는 반응하지만 여섯 개에서는 어려워한다는 사실을 알지 못한다. 어떤 안내 문구가 길고, 어떤 그림이 이해에 도움이 되며, 실제 생활에서 어떤 순서 연습이 필요한지는 교사가 훨씬 잘 안다. 이 지식을 설계 문서에 넣으면 AI의 구현 능력과 교사의 교육적 판단이 결합된다.

**근거:** [1]

## 06. 오늘의 큰 흐름

전체 흐름을 지도처럼 보여주는 장이다. 먼저 AI가 일하는 환경을 이해하고, 그 다음 프로젝트를 어디에 두고 어떤 지침을 둘지 본다. 이후 좋은 서비스와 UX를 다룬 뒤 DESIGN.md와 시각적 도안으로 넘어간다. 마지막에는 구현·검증·배포를 연결하고 오성학교용 작은 실습 프로젝트를 진행한다. 중간에 도구가 많이 나오더라도 이 큰 흐름 안에서 위치를 잡으면 된다.

**근거:** [1]

## 07. Harness Engineering

하네스는 AI에게 한 문장 프롬프트를 던지는 것이 아니라, 일을 잘할 수 있는 주변 환경까지 마련해 주는 관점이다. 학교에 비유하면 업무 규정, 업무편람, 담당자, 사용할 시스템, 점검 절차가 함께 있는 상태다. 코딩 Agent에게도 비슷하게 규칙 파일, 설계 문서, Skills, 도구 연결, 테스트, 세션 인계가 필요하다. 오늘은 하네스를 가장 큰 틀로 사용한다.

**근거:** [1]

## 08. 하네스 안에는 무엇이 들어갈까?

각 도구마다 폴더명이나 기능 이름은 조금씩 다르다. 따라서 이름을 외우기보다 ‘무슨 문제를 해결하는가’를 기준으로 이해한다. 항상 지켜야 하는 규칙, 프로젝트의 안정적인 지식, 반복 가능한 작업법, 특정 역할을 맡는 Agent, 자동으로 실행되는 절차, 외부 서비스와 연결하는 도구가 핵심이다. 이 틀을 알면 Claude Code에서 배운 개념을 Codex나 Antigravity로 옮기기 쉬워진다.

**근거:** [1], [7], [8]

## 09. Loop Engineering

Loop는 ‘계속 알아서 해’가 아니다. 무엇을 검사하고, 실패하면 어디로 돌아가며, 언제 끝낼지를 정하는 것이다. 예를 들어 UI 하나를 구현한 뒤 빌드하고, 오류가 있으면 수정하고, 화면을 확인한 뒤 기준을 만족하면 종료하는 루프를 만든다. 반복 규칙이 없으면 Agent는 같은 실패를 되풀이하거나 필요 이상으로 검증을 계속할 수 있다.

**근거:** [1]

## 10. 좋은 Loop에는 종료 조건이 있다

Agent에게 반복 작업을 맡길 때는 종료 조건을 명확히 해야 한다. 예를 들어 ‘버튼이 클릭된다’, ‘저장이 유지된다’, ‘화면 폭 768px에서도 깨지지 않는다’처럼 눈으로 확인 가능한 기준이 좋다. 무한 반복을 막기 위해 최대 반복 횟수나 사람이 판단해야 하는 조건도 둔다. 교사 업무로 치면 공문 초안을 계속 수정하게 하는 것이 아니라, 형식·내용·맞춤법 기준을 통과하면 검토 요청으로 넘기는 것과 같다.

**근거:** [1]

## 11. Graph Engineering

Graph는 여러 Agent나 사람에게 일을 나누고 결과를 어디로 넘길지 설계하는 관점이다. Planner가 요구사항을 정리하고, UI/UX Designer가 화면을 설계하고, 구현 Agent가 코드를 만들고, Reviewer와 Verification이 서로 다른 방식으로 검사한 뒤 배포하는 흐름이 한 예이다. 각 단계 안에서는 다시 Loop가 돌아갈 수 있다.

**근거:** [1]

## 12. Harness · Loop · Graph를 한 문장으로

세 용어를 어렵게 기억할 필요는 없다. Harness는 전체 환경, Loop는 한 사람이 일을 끝낼 때까지의 반복, Graph는 여러 담당자 사이의 흐름이다. 학교로 비유하면 학교의 업무 체계가 Harness, 한 담당자의 업무 처리 절차가 Loop, 부장-담당자-관리자 사이 결재와 인계가 Graph에 가깝다. 이 세 층을 구분하면 Agentic coding 관련 용어를 훨씬 쉽게 이해할 수 있다.

**근거:** [1]

## 13. 왜 교사에게 이 관점이 필요한가

교사의 AI 활용에서도 하네스는 유용하다. 학급이나 학교 업무에서 반복되는 문체, 개인정보 원칙, 학생 수준, 자료 형식 등을 문서로 두면 매번 긴 프롬프트를 다시 쓰지 않아도 된다. 바이브코딩에서는 효과가 더 크다. 프로젝트가 며칠 이상 이어지면 현재 상태와 결정 이유를 남기지 않을 경우 새 세션이 처음부터 다시 탐색하는 비용이 커진다.

**근거:** [1]

## 14. 실제 하네스 사례: Everything Claude Code

Everything Claude Code는 공개된 대규모 Claude Code 하네스 사례다. 강의에서는 이것을 그대로 설치하자는 뜻이 아니라, 규칙·스킬·에이전트·훅·MCP·검증이 어떻게 하나의 작업 체계로 묶이는지 보여주는 참고 사례로 사용한다. 저장소는 Anthropic 관련 해커톤 우승자의 실제 설정을 기반으로 한다고 소개하고 있다. 중요한 것은 규모를 따라 하는 것이 아니라 필요한 구성만 선택하는 것이다.

**근거:** [10]

## 15. Rules / AGENTS.md / CLAUDE.md

Rule은 매 작업마다 바뀌는 요청이 아니라 프로젝트 전반에서 계속 지켜야 하는 원칙이다. 예를 들어 기존 학생 데이터 구조를 함부로 바꾸지 않기, 모바일을 고려하기, 요청하지 않은 대규모 리팩터링을 피하기 같은 내용이다. Codex는 AGENTS.md를 저장소 루트에서 현재 작업 폴더까지 읽어 지침을 합치는 방식이 문서화되어 있다. 따라서 상위·하위 규칙을 나누는 설계가 가능하다.

**근거:** [1], [9]

## 16. Docs

Docs는 비교적 안정적인 프로젝트 지식을 담는다. 프로젝트 목적, 대상 사용자, 화면 설계, 데이터 구조, 배포 방식처럼 여러 세션에서 계속 참고해야 하는 정보를 모은다. Rule과 달리 ‘반드시 지켜라’보다는 ‘이 프로젝트는 이런 구조다’에 가깝다. 문서가 잘 정리되면 새 Agent가 전체 코드를 무작정 읽기보다 먼저 설계 의도를 이해할 수 있다.

**근거:** [1]

## 17. Skills

Skill은 반복 가능한 업무 매뉴얼이다. 예를 들어 UI Review Skill이라면 화면 목적 확인, 정보 위계, 주요 버튼, 모바일 대응, 접근성, 개선안 작성 순서를 정의할 수 있다. Rule이 ‘항상 지켜야 하는 원칙’이라면 Skill은 ‘이 일을 할 때 따라갈 방법’이다. 최근 Codex 계열에서도 SKILL.md 기반의 재사용 워크플로우가 공식적으로 강조되고 있다.

**근거:** [1], [8]

## 18. Agents

Agent는 역할이 있는 작업자다. Skill이 매뉴얼이라면 Agent는 그 매뉴얼과 도구를 사용해 일을 맡는 담당자에 가깝다. 모든 작업을 한 Agent에게 몰아주는 것보다, 복잡한 프로젝트에서는 탐색·설계·구현·검토를 분리했을 때 컨텍스트가 더 선명해질 수 있다. 다만 작은 실습에서는 Agent를 과도하게 쪼개지 않고 필요할 때만 분리하는 것이 좋다.

**근거:** [1], [7]

## 19. Hooks

Hook은 특정 사건에 반응하는 자동화 규칙이다. 사용자가 매번 ‘포매터 돌려줘’, ‘상태 저장해줘’라고 말하지 않아도 되도록 한다. 훅이 지원되는 도구에서는 세션 시작·종료, 도구 호출, 파일 변경 같은 시점에 자동 처리를 걸 수 있다. 중요한 것은 자동화가 많을수록 좋은 것이 아니라, 반복적이고 결정적인 작업에만 적용하는 것이다.

**근거:** [1]

## 20. Commands / Workflows

Command나 Workflow는 사람이 자주 하는 작업을 짧게 호출하는 입구다. 재사용 가능한 실제 작업 논리는 Skill에 두고, Command는 그것을 호출하는 짧은 시작점으로 보는 방식이 이해하기 쉽다. Antigravity는 공식 문서에서 Rules와 Workflows를 사용자 맞춤 기능으로 제공한다. 중요한 것은 명령 이름이 아니라 동일한 절차를 매번 다시 설명하지 않도록 만드는 것이다.

**근거:** [1], [7]

## 21. Memory / Handoff

프로젝트 지식과 작업 상태를 구분해야 한다. DESIGN.md처럼 비교적 안정적인 내용은 Docs이고, ‘지금 어디까지 만들었는지’는 계속 바뀌는 상태다. 세션이 길어지면 CURRENT_STATE.md나 HANDOFF.md에 현재 상태를 외부화하고 새 세션이 이어받도록 한다. 채팅 기록 전체를 억지로 유지하는 것보다 핵심 상태를 압축해 넘기는 것이 효율적이다.

**근거:** [1]

## 22. MCP / Tools

MCP와 Tool 연결은 Agent가 말만 하는 존재에서 실제로 자료를 읽고 작업하는 존재로 바꾸는 역할을 한다. 예를 들어 GitHub를 연결하면 저장소를 읽고 수정할 수 있고, Figma를 연결하면 디자인 컨텍스트를 가져오거나 지원되는 환경에서는 캔버스에 디자인을 쓸 수 있다. 도구가 늘어날수록 권한과 안전 기준도 중요해지므로 필요한 것만 연결하는 것이 좋다.

**근거:** [1], [5]

## 23. 도구가 달라도 개념은 비슷하다

Claude Code, Codex, Antigravity가 같은 파일 구조를 쓰는 것은 아니다. 그러나 프로젝트 지침, 재사용 작업법, 전문 작업자, 자동화, 외부 도구라는 역할은 상당 부분 공통적이다. 새로운 도구가 나와도 ‘이 제품에서는 규칙을 어디에 두나’, ‘반복 작업을 어떻게 재사용하나’, ‘외부 도구를 어떻게 연결하나’를 보면 빠르게 적응할 수 있다.

**근거:** [1], [7], [8], [9]

## 24. 프로젝트 폴더는 어디에 둘까?

처음 바이브코딩을 시작할 때 자주 헷갈리는 부분이다. Codex나 Claude가 만드는 숨김 설정 폴더는 도구 자체의 전역 설정 공간에 가깝다. 실제 프로젝트는 문서 폴더나 별도의 Projects 폴더처럼 사람이 찾기 쉬운 위치에 둔다. 그 폴더를 Claude Code, Codex, Antigravity에서 열어 작업하면 된다.

**근거:** [1]

## 25. 전역 설정과 프로젝트 설정

전역 설정은 모든 프로젝트에 공통으로 적용하고 싶은 내용에 적합하다. 반면 특정 학교, 특정 서비스의 학생 정보 구조나 디자인 규칙은 프로젝트 안에 두는 것이 안전하다. 그래야 저장소를 다른 컴퓨터나 다른 Agent가 열어도 필요한 맥락이 함께 이동한다. 공통 설정에 프로젝트별 내용을 너무 많이 넣으면 다른 프로젝트에도 불필요한 컨텍스트가 섞인다.

## 26. 상위·하위 지침
